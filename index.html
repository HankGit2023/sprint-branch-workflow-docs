02 — 現行流程

現行流程的三個痛點

問題不是紀律不夠，而是 forQA 同時身兼兩個互相衝突的角色。

痛點 01

需求分支彼此隔離

同期所有需求分支都從 dev2 切出，彼此完全看不到對方代碼。若兩個需求有相依性，開發階段無法互相使用對方尚未合併的代碼。

痛點 02

forQA 改了沒意義

forQA 是打包用的匯流分支，QA 在這裡第一次看到大家的代碼相遇。但 forQA 上的修改下次合併就會被蓋掉，衝突/相依問題在自己需求分支也看不到對方，兩邊都無法修。

痛點 03

手動合併的風險

發版時主管手動把各需求分支合併到發版分支，容易和 forQA 實際測過的狀態不一致（過去已發生 OKF-1332 合併參數遺失的事故）。

03 — 新版流程

新版流程的核心機制

四個機制環環相扣，共同解決「隔離」與「不一致」兩個問題。

機制 01

Sprint 分支持續存在

取代 forQA，作為這期唯一的整合分支。需求分支從這裡切出，也合併回這裡；QA 直接從這裡打包驗證。

機制 02

雙向同步

需求分支開發期間要定期把 sprint 分支同步回自己（單人分支可 rebase + force-push，多人共修用 merge），相依問題提早在自己分支發現並修復。

機制 03

一次 revert 就乾淨

每個需求對 sprint 分支都是一個完整的 merge commit，需要下架時 git revert -m 1 一次搞定，不需要事先 squash。

機制 04

Release 分支即歷史紀錄

主管從 sprint 分支切出 release，可選擇性 revert；一提審就合回 dev2（不等審核），release 分支保留不刪，成為每個版本的歷史紀錄。

恢復時機明確

Git Revert 路徑

以 tag 為基礎重新評估、cherry-pick 舊代碼再調整——不要單純 revert-the-revert，主線和需求本身可能都已變化。

恢復時機不確定

Feature Flag 路徑

代碼照常合併上線、開關關閉即可，要恢復時直接開開關，不用處理跨 sprint 的 revert / un-revert。

08 — 規則總覽

合併與同步規則

四條可以直接寫進開發規章的規則，供會議定案。

1

Merge / Rebase 依所有權決定

貢獻進 sprint 分支一律用 merge --no-ff；同步回單人開發的需求分支可用 rebase + force-push，多人共修才需要 merge。

2

禁止 squash-merge 進 sprint 分支

Merge commit 本身 revert 已是原子操作，squash 對此沒有幫助，卻會切斷同步與 rebase --onto 所需的歷史關聯。

3

已合併分支不回頭改寫歷史

合併前可自由用 rebase -i 整理 commit；合併後即結案，續做一律開新分支。

4

延期／延遲一律要可追蹤

打 tag、commit 訊息標單號、同步更新 JIRA 狀態，確保未來任何人都能找到恢復的起點。

09 — 待定案

開放討論問題

三點需要團隊會議共識才能定案；一點已實測驗證，附上結論給大家參考。

Q1

Sprint 分支何時凍結？

release 分支切出後，dev_0903 是否立刻視為凍結、不再接受 commit？若還有人繼續提交，revert 語意會混亂——更嚴重的是，dev_0903 本身不會合回 dev2（只有 release_xxx 會），凍結後才提交的 commit 會變成孤兒，永遠進不了 dev2。

建議方案（待會議確認） 切 release 的當下就是凍結時刻，且要公告不是默契——主管切 release 前先在群組預告、給緩衝時間，時間到就切且視為凍結。凍結後若還要修東西，直接上 release_xxx（同「提審被拒修復路徑」邏輯）。可考慮用 GitLab 分支保護規則技術上強制唯讀，不完全依賴人記得。sprint 分支本身不用像 release 分支永久保留，合併完成後可以刪除。
Q2

選擇性 revert 夠用嗎？

新設計刻意讓需求分支互相依賴，一旦真的產生相依，release 分支單獨 revert 某需求可能無法乾淨移除——要不要搭配 feature flag？

✓ 已解決

打包工具吃得下動態分支名嗎？

已實測確認：/send-build 不綁死分支名，直接打包當前分支；Telegram 路由表的全域預設本來就跟 forQA 現在指向同一個群，動態 sprint 分支不用改任何設定就能用，不需要保留 forQA。

Q4

雙向同步的頻率？

需求分支多久要同步一次 sprint 分支？需要團隊訂出具體規則（如每日、每次要重驗前）。
